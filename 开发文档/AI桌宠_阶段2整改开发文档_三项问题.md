## 3. S2-F01：收紧自定义文件操作命令权限

### 3.1 问题与根因

基线中的 `copy_dir(from_path, to_path)` 直接创建目标目录并复制内容，没有调用窗口检查，也没有在 Rust 中限定复制目标。该命令注册在 `invoke_handler` 中。[R1][R2]

目前正常导入入口位于 `preference`，由前端生成资源 ID，并把目录复制到应用数据目录的 `custom-models/<id>`。[R3]

Tauri 官方说明，应用经 `invoke_handler` 注册的命令默认可供应用窗口/WebView 调用；要限制应用命令，需要额外配置或校验。因此，不能把“从聊天窗口移除了 `fs` 插件权限”当成“已限制自定义 Rust 文件操作命令”。[D1]

**整改边界：**这是应用命令访问控制缺口，不是已确认的数据泄露事件；本轮修复这一入口及其直接关联权限，不宣称完成整个应用安全审计。

### 3.2 必须实现的行为

#### A. 调用者由后端识别

- `copy_dir` 或其替代导入命令只允许实际负责导入的 `preference` 窗口调用。
- `chat`、`main` 和其他非授权窗口应在产生文件系统副作用之前被拒绝。
- 使用 Tauri 注入的窗口/WebView 上下文判断调用方，不能信任前端参数中的 `windowLabel`、`isAdmin` 或类似字段。
- 可以使用应用命令 ACL、Rust 命令内校验或两者结合；必须证明最终权限生效，不把只修改 JSON 当作验收完成。
- 若修改 `build.rs` 或应用命令清单，同步验证所有仍需调用的命令，避免修复复制权限后导致聊天或设备初始化失效。

#### B. 目标目录由后端约束

本轮合法目标是应用自己的模型导入目录，不能保留通用任意目录复制能力。

**优先方案：**由 Rust 确定应用数据目录，构造 `custom-models/<资源ID>`；前端传入源路径和必要的资源标识，后端返回实际导入路径。资源 ID 必须是安全的单一路径组件，不能用它携带目录跳转。

**兼容方案：**保留现有参数，但在 Rust 内核验目标确属 `custom-models` 下的合法、独立子目录。不能仅做字符串前缀比较，也不能只信任前端已经检查过路径。

两种方案择其一，不同时保留一个仍可绕过校验的旧复制命令。

需要覆盖：目标根目录本身、根目录外路径、目录跳转、同名前缀的其他目录，以及符号链接等路径重定向。目标尚不存在时，应基于可信且已验证的父目录构造新目录，不能直接对不存在的完整路径调用规范化后就放弃校验。

#### C. 源目录仍支持正常用户导入

- 保留从用户选择或拖入的外部模型目录导入的能力，不把源路径一律限制在应用目录中。
- Rust 确认源路径存在、是目录，并按当前加载器支持的模型资源结构进行必要验证；不要未经核对就缩减已支持的模型类型。
- 不以一个前端传来的“用户已选择”布尔值作为目录安全校验。
- 对源目录树中的符号链接及同类路径重定向采用明确策略。可在本阶段拒绝并给出提示，或验证实际读取范围不越出源树；不能默默跟随到任意位置。
- 防止源目标相同、相互包含或递归复制自身等异常情况。
- 无效调用不得创建目标目录；真实复制中途失败时，只清理本次新建且已确认归属的临时/目标目录，绝不能递归删除用户源目录或已有模型。
- 导入未完整成功，不向模型列表写入一个“成功”的资源条目。

这些是本轮路径边界要求，不表示普通目录校验已解决所有并发文件系统攻击问题；未覆盖的限制须如实记录。

#### D. 核查其他自定义命令

核对 `invoke_handler` 中的文件、设备和凭证命令，形成简短“命令 → 合法调用窗口”表。只调整有明确越权风险或因本次 ACL 改动受影响的部分，不做无关系统重构。

保持既有 Key 窗口边界，不因解决导入问题让 `main` 获得读取 Key 的能力；不要给全部窗口授予通配权限来消除报错。

## 4. S2-F02：修复读取 Key 期间取消无效

### 4.1 问题与复现证据

基线中 `begin()` 设置发送状态，随后等待 `getAIKey()`；`AbortController` 到 `execute()` 才创建，而 `cancel()` 仅执行 `controller?.abort()`。[R4]

```text
开始 send/retry
  → sending = true
  → 等待 getAIKey() 返回
  → 用户点击取消：此时 controller 可能仍为空
  → Key 返回
  → 创建控制器并继续调用 AI 客户端
```

既有隔离记录中，首次发送与重试都复现了“取消后仍新增一次 AI 客户端调用”。该调用是测试替身调用，不是已测得真实服务商请求或扣费。[E1]

### 4.2 修复后的产品行为

| 时点或操作             | 必须行为                                                                    |
| ---------------------- | --------------------------------------------------------------------------- |
| 等待 Key 时取消        | 本次流程立即失效，不等待 Key 返回才释放界面；之后 Key 返回也不能继续调用 AI |
| HTTP 已开始后取消      | 向现有客户端/transport 传递取消，同时阻止迟到结果写回                       |
| 读取响应体期间取消     | 停止客户端等待，旧响应不能新增助手消息                                      |
| 重试时取消             | 复用的用户消息退出 pending，仍只保留一份问题和原 `turnId`                   |
| 取消后立即发送新问题   | 新任务正常开始；旧任务完成、失败或 finally 均不能改变新任务状态             |
| 清空会话               | 同时取消旧任务并改变会话版本；旧问题、回复、错误均不回流                    |
| 隐藏聊天窗口           | 维持阶段 2 原行为：保留会话，允许在途请求正常结束，不等同于销毁页面         |
| 真正销毁页面或退出应用 | 终止/隔离当前本地任务，不留下可回写的旧流程                                 |

**取消前尚未产生消息气泡的情况：**保留“缺少 Key 不追加消息”的现有规则；如果取消发生在读取 Key 阶段，问题还未进入消息列表，则恢复到输入草稿或保留为可编辑草稿。不得丢掉用户输入，也不得覆盖用户随后输入的新草稿。若该问题已经有气泡，则将其标为 `cancelled`，不另外复制一条。

上述早期取消的草稿规则是为修复时消除歧义而补充的验收细则，不要求新增聊天历史、自动重试或新会话系统。

### 4.3 实现约束

1. **取消覆盖全生命周期。**在第一次异步等待之前建立请求标识、会话版本和取消状态。不要只把控制器往前挪，却仍让界面一直等凭证 Promise 完成。
2. **请求对象属于当前任务。**每次首次发送或重试创建独立 `requestId` 与运行态；不让新任务复用一个已经中止的控制器。
3. **异步边界后检查有效性。**至少覆盖 Key 返回、调用客户端之前、收到回复、异常处理和最终清理。
4. **取消后的凭证回调只能被丢弃。**不要求强行取消已经发出的 Rust IPC；要求即使它稍后成功或失败，也没有新的网络调用和界面副作用。
5. **保留 requestId/sessionVersion 防护。**旧任务不能清除新任务的控制器、`sending` 或消息，不能在清空后显示旧错误提示。
6. **同步维护 UI 行为。**必要时更新 `SendResult` 和 `handleSend()`，明确区分用户取消、过期任务与真正错误，避免恢复过期草稿或吞掉输入。
7. **不改变存储与隐私边界。**控制器、Promise、Key 和请求运行态不进入可序列化 store 或跨窗口事件。
8. **不引入自动重试。**取消客户端不保证服务商已停止计算或计费，文案不得承诺“取消就不扣费”。

可以采用单个请求运行态对象、可取消等待封装或其他等价方案。以上约束是验收合同，不指定唯一代码写法；对不可取消的底层 Promise 要处理迟到拒绝，不能制造未捕获异常。

## 5. S2-F03：补齐模型加载失败回退与恢复

### 5.1 问题与根因

`useModel.ts` 在加载失败后返回 `false`；主窗口仅在成功时绑定模型，但没有在失败时调度回退，后续还会继续处理背景/按键资源并设置 `modelReady`。[R5][R6]

因此当前缺少的是完整恢复流程，不是只有一条错误提示。原阶段 2 文档已要求：模型不可用时回退展示，保留宠物身份与人格。[P1，任务 2.2]

### 5.2 本轮必须覆盖的触发场景

当前模型目录被移动或删除、入口模型文件或关键资源损坏、路径存在但渲染器拒绝加载，以及用户切换到不可用模型。

不要只检查目录 `exists()` 就认为加载成功；必须以实际加载结果为准。

### 5.3 回退流程

```text
尝试加载用户当前选择的模型
  ├─ 成功：使用本次加载快照提交展示与绑定
  └─ 失败：记录本次失败，不标记展示成功
       → 从已有内置模型中选择未尝试的候选
       → 逐个尝试，每个候选在本次恢复周期最多一次
       ├─ 某个成功：切换到该模型，提示已回退，更新实际绑定
       └─ 全部失败：结束加载等待，显示可恢复错误与设置/重试入口
```

本轮优先尝试内置 `standard` 模型，其后按项目确定且稳定的顺序尝试其他内置候选；已失败者不重复加入。实际模型清单以当前代码为准，不硬编码一个不存在的资源路径。

不下载新模型，不自动修复用户源文件，不遍历全盘寻找替代资源。

### 5.4 宠物档案与资源记录的边界

| 字段/对象               | 回退时要求                                                     |
| ----------------------- | -------------------------------------------------------------- |
| `pet.profile.id`        | 保持原值，不重新生成                                           |
| 名字、人格、`createdAt` | 保持原值，不重置为默认值                                       |
| `pet.profile.modelId`   | 只有真实加载成功时，才更新为实际展示的资源 ID                  |
| 本次聊天                | 不因换外观而清空，不创建另一只宠物                             |
| 不可用自定义模型记录    | 不自动删除原文件或资源记录；保留用户后续修复/管理的可能        |
| 内置模型都失败          | 不把候选 ID 写成已成功绑定，不覆盖原档案；标明当前没有成功展示 |

默认宠物初始化仍由 `main` 在载入存档后幂等执行。回退不是“重新领养”，不能调用会重建 ID 的初始化路径来绕开问题。

### 5.5 加载状态必须真实且可恢复

- 区分“正在加载”“成功展示”“终止于错误”。可增加最小错误状态或等价实现，不要求建立大型状态机。
- 不能用 `modelReady = true` 冒充渲染成功。
- 也不能让全部候选失败后继续保持无限转圈。
- 现有设置页有与模型加载相关的遮罩。必须同步检查：失败后仍能进入模型设置和发起明确的重试，不被全屏遮罩永久挡住。
- 将失败提示限制在适当频率。一次恢复流程结束后给出清晰结果，不能每帧/每次 watcher 重触发都弹窗。
- 展示文案示例：“当前模型无法加载，已切换为内置模型；宠物档案保持不变。”全部失败时提示检查资源、重新选择或重试，不向用户声称已经自动修好。

### 5.6 防止回退触发新的竞态

模型加载、背景资源、按键映射和 `pet.modelId` 应属于同一次加载快照。不要在 `await` 之后无条件读取可能已经变更的 `currentModel.id` 并与旧模型加载结果组合。

若用户快速选择 A、B，A 较晚完成，最终应以最新有效选择 B 为准；A 的回退任务不能把 B 覆盖。可使用加载代次、取消机制或串行调度，结合实际渲染器接口实现。

**如果渲染器是共享单例，仅防止旧任务写 store 还不够。**要确认旧加载本身不会晚到后替换画布。不得假设第三方库提供了尚未核实的取消 API。

回退引起 `currentModel` 变化时，应避免另一个 watcher 又开启同一恢复链。每个候选尝试次数有界，失败与清理路径都能退出。

### 5.7 文件修改建议

| 文件                                           | 预期职责                                          |
| ---------------------------------------------- | ------------------------------------------------- |
| `src/stores/model.ts`                          | 必要的加载/错误信息与候选选择，不承载宠物身份重建 |
| `src/composables/useModel.ts`                  | 清晰返回真实加载结果，按本次模型快照处理资源      |
| `src/pages/main/index.vue`                     | 主窗口唯一协调加载、回退、展示与成功后绑定        |
| `src/stores/pet.ts`                            | 继续保持身份稳定；通常只复用现有绑定接口          |
| `src/pages/preference/index.vue`、相关提示文本 | 失败后解除阻塞，保留模型管理/重试入口             |
| 新增或扩展模型加载测试                         | 覆盖失败回退、候选耗尽、档案不变及迟到加载        |

### 5.8 验收用例

| 编号   | 场景                                 | 必须结果                                                   |
| ------ | ------------------------------------ | ---------------------------------------------------------- |
| F03-01 | 当前自定义模型目录丢失后重启         | 自动回退可用内置模型；原 ID、名字、人格、创建时间保持不变  |
| F03-02 | 目录存在但模型入口/关键资源损坏      | 同样触发回退，不把目录存在视为成功                         |
| F03-03 | 使用中切换到坏模型                   | 恢复可用展示；已有聊天不清空；界面可继续操作               |
| F03-04 | 首个内置候选也加载失败               | 尝试后续未试候选，成功后只绑定实际成功模型                 |
| F03-05 | 全部候选失败                         | 有界结束、不假装 ready、不永久遮挡设置；可选择资源或重试   |
| F03-06 | A/B 快速切换，A 的成功或失败迟到     | 最终展示、资源映射和绑定均属于最新有效请求，不被旧回退覆盖 |

| F03-09 | 成功回退后正常退出重启               | 恢复稳定档案与合法展示；不重复生成 ID                      |

至少补模型调度/状态逻辑自动化测试，并在真实 Tauri/Live2D 中执行 F03-01、F03-03、F03-05。全部失败可使用受控故障注入，不破坏用户正式模型或应用安装资源。简单 mock 渲染成功不等于真实 Live2D 回退效果已通过。
